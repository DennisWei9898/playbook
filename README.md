# 從 Idea 到 MVP：Claude Code 輔助產品開發操作手冊

> 把任何商業 Idea 帶進來，走完這份流程，就能產出可上線的 Phase 1 MVP。
> 所有 Skills 放在 `skills/` 子目錄，複製到自己的專案即可啟用。

---

## 資料夾結構

```
playbook/
├── README.md               ← 本文件（操作手冊）
└── skills/
    ├── research/           ← 競品調查與市場研究（含進階：競品評分矩陣）
    ├── feature-plan/       ← 功能規劃與任務拆解
    ├── qa-review/          ← BDD 測試與 QA 報告
    ├── sdd-update/         ← 技術文件同步維護
    ├── idea-to-mvp/        ← 全流程引導（整合 skill）
    │
    │  ── 進階整合 Skills（從 atomic skills 上一層）──
    ├── auto-research/      ← 多輪並行研究 orchestrator（自動拆題 + 並行 spawn）
    └── eli5-pptx/          ← ELI5 簡報生成（4 配色 + python-pptx helpers）
```

**安裝 Skills**：

```bash

# 推薦版：搭配 G-Stack 加值（選配）

#    詳見 https://github.com/getsentry/gstack 或對應安裝指南

cp -r playbook/skills/* ~/.claude/skills/
```

## 與 G-Stack 的關係（軟相依）

本 Playbook 的核心 5 個 skill **完全自帶能力**，不需任何外部套件即可運作。
但如果使用者已經安裝 [G-Stack](https://github.com/getsentry/gstack)，本 Playbook 會在對應 Phase **偵測並建議**搭配以下 G-Stack skill 加強體驗：

| Phase | 自帶能力 | G-Stack 加值（偵測到才建議） |
|-------|---------|---------------------------|
| Phase 0 | 內建 Problem Statement Canvas | `/office-hours` — YC 風格逼問 6 題 |
| Phase 5 | 內建 `/feature-plan` | `/plan-ceo-review` — scope 送審；`/plan-eng-review` — 架構審 |
| Phase 7 | 內建 `/qa-review`（BDD 規格） | `/qa` — 對 live site 跑測試並自動修；`/design-shotgun` — UI 變體探索；`/design-review` — 視覺審查 |
| Phase 7 結尾 | 自動 commit | `/ship` — PR 流程（測試 + version + commit + push） |

**為什麼不直接 bundle G-Stack？**
- G-Stack 是獨立套件（`/gstack-upgrade` 自動更新），複製進來會死在某個版本無法跟上
- 體積大，會稀釋 Playbook 的核心定位
- 套件分離後，使用者可以選擇是否要這層加值

偵測邏輯：本 skill 在執行前會用 `ls ~/.claude/skills/{skill-name}/SKILL.md` 偵測，若不存在則直接走 fallback。

## Phase 0：Idea 定義

### Problem Statement Canvas

用一段話說清楚「誰、在什麼情境、遇到什麼問題、為什麼現有方案不夠好、我怎麼解決得更好」：

```
[目標用戶] 在 [具體情境] 下，
面臨 [痛點]，
現有方案 [失敗原因]，
我的方案透過 [核心機制]，解決得更好。
```

### 檢核點

- [ ] 這個痛點有你自己或身邊人的真實案例嗎？
- [ ] 估算過市場規模嗎（TAM / SAM / SOM）？
- [ ] 你有不對稱優勢嗎（資源、人脈、資料、技術、垂直領域知識）？

## Phase 1：商業調查（`/research`）

### 研究不只做一次

`/research` 貫穿整個開發過程，遇到問題就觸發：

| 時機 | 觸發原因 | 示例問題 |
|------|---------|---------|
| 專案啟動 | 了解市場現況與競品格局 | 「[你的賽道] 主要競品有哪些？他們怎麼增長的？」 |
| 功能設計前 | 找最佳實踐參考 | 「[相似功能] 在成熟產品裡怎麼設計？」 |
| 遇到技術/法律問題 | 確認可行性與風險 | 「[你要做的事] 有法規限制或 API ToS 問題嗎？」 |
| 商業模式調整 | 驗證變現方向 | 「[你的變現方式] 在同類產品裡行不行得通？」 |
| 開發中遇到設計卡點 | 找現成解法 | 「[你的問題場景] 業界怎麼處理？」 |

### 典型研究路徑（五輪）

一個完整的 0→1 專案，研究通常分五輪展開：

#### 第一輪：競品核心研究（專案啟動，1-3 天）

目標：理解你的賽道裡，哪些成功產品用了什麼飛輪，以及你最想借鑑的 1-2 個機制是什麼。

| 研究類型 | 研究問題 |
|---------|---------|
| 直接競品分析 | `[競品名稱] 的商業模式與增長飛輪是什麼？` |
| 成功案例借鑑 | `[成功產品] 怎麼做冷啟動 / 留存 / 變現？` |
| 交叉對比 | `[A 產品] vs [B 產品] 的核心差異是什麼？對我的啟示？` |

#### 第二輪：競品 UX 深度研究（啟動後 1 週內）

目標：實際體驗競品流程，找到差異化的設計機會點。

| 研究類型 | 研究問題 |
|---------|---------|
| 核心流程 UX | `[競品] 的 [核心流程] 步驟如何設計？摩擦點在哪？` |
| 冷啟動策略 | `[競品] 早期怎麼解決「0 內容/0 用戶」問題？` |
| 差異化機會 | 「多數競品在哪個環節做得不夠好，是我能做更好的地方？」 |

#### 第三輪：深度功能研究（開發前，針對核心功能）

目標：在動手寫程式碼前，確認每個核心功能的設計決策有依據。

| 研究類型 | 研究問題 |
|---------|---------|
| 市場規模 | `[你的賽道] TAM/SAM/SOM 怎麼估算？` |
| 核心機制設計 | `[你的核心功能] 在同類產品中有哪些設計模式？` |
| 可行性驗證 | `[你需要的技術/API/資料] 在 [你的地區] 有沒有限制？` |
| 商業模式細節 | `[你的變現方式] 定價怎麼設？競品收費模式是什麼？` |

#### 第四輪：開發過程中補充研究（依需求觸發）

目標：開發中遇到設計卡點時，不靠猜測，用研究決策。

| 研究類型 | 研究問題 |
|---------|---------|
| 互動設計細節 | `[你要實作的互動] 業界有哪些好的範例？` |
| 留存機制 | `[你的產品類型] 常見的留存策略有哪些？` |
| 技術方案選型 | `實現 [你的功能需求] 有哪些技術方案？各自的代價？` |

#### 第五輪：商業規模研究（開發後期 / 準備上線前）

目標：確認上線後的商業路徑，並排除法律/合規風險。

| 研究類型 | 研究問題 |
|---------|---------|
| 變現路徑 | `[你的資料/功能] 能包裝成哪些 B2B 或 B2C 產品？` |
| 合規與風險 | `[你整合的第三方服務/資料] 有沒有使用限制或法律風險？` |
| 定價 Benchmark | `同類產品的定價區間是多少？用戶接受的上限在哪裡？` |

### 呼叫方式

```
/research [你的研究主題]
```

輸出自動存到 `reports/{主題}-research-{YYYY-MM-DD}.md`

## Phase 2：假設提煉

### 差異化三角

從研究中提煉你的核心差異化，用三個維度描述：

```
[維度 1：你比競品更「可信/可靠」的地方]
  ×
[維度 2：你比競品更「有用/有效」的地方]
  ×
[維度 3：你比競品更「好用/低摩擦」的地方]
```

### 核心假設清單

列出 3-5 個核心假設，標出「哪個假設如果錯了，整個 Idea 就不成立」：

```
H1（致命假設）：[目標用戶] 願意因為 [你的核心差異]，
               從 [現有方案] 轉用你的方案。

H2：[用戶族群] 在 [具體情境] 中，
    會自發地完成 [你期待的核心行為]。

H3：[你的商業機制] 能在達到 [某個規模] 後，
    形成自我強化的飛輪。
```

## Phase 3：商業模式設計

### 從成功案例借鑑飛輪

研究完競品後，不要從零發明，而是找可移植的增長機制：

| 飛輪類型 | 代表案例 | 核心原理 | 適合的產品類型 |
|---------|---------|---------|--------------|
| UGC 信任飛輪 | 小紅書、Yelp | 內容越多 → 信任越高 → 更多人加入 → 更多內容 | 評論、社群、知識平台 |
| Freemium 積分牆 | Canva、Medium | 免費體驗 → 在「最想要答案」的瞬間觸發付費 | 內容解鎖、工具類 |
| 連續行為獎勵 | Duolingo、健身 App | 每日習慣 → 連續達成獎勵 → 高留存 | 需要養成習慣的產品 |
| 供需雙邊飛輪 | Airbnb、Uber | 供給增加 → 需求提升 → 供給更多 | 市集、媒合平台 |
| 病毒分享飛輪 | Dropbox、Canva | 使用產品的行為本身帶來新用戶 | 協作工具、展示型產品 |

**選擇你的飛輪**：從上表選 1-2 個最適合你 Idea 的飛輪，用你自己的場景填入：

```
借鑑來源：[產品名]
飛輪原理：[A] → [B] → [C] → [A]（循環）
我的版本：[套入你的場景]
啟動條件：要達到什麼規模 / 狀態，飛輪才會轉起來？
```

### 常見變現模式選型

| 模式 | 適合場景 | 代表案例 | 關鍵問題 |
|------|---------|---------|---------|
| 訂閱制 | 持續提供價值的工具/內容 | Notion、Spotify | 用戶願意每月付多少？ |
| 交易抽成 | 媒合買賣雙方 | Airbnb、Etsy | 交易頻率夠高嗎？ |
| Freemium + 進階功能 | 個人先免費、團隊付費 | Slack、Figma | 免費版的邊界在哪裡？ |
| 積分牆（內容解鎖）| 資訊密集型平台 | Medium、知識星球 | 哪個「關鍵資訊點」值得付費解鎖？ |
| 廣告 | 高流量內容平台 | Google、小紅書 | 流量要多大才值得？ |
| 數據 / API | 有獨特資料積累 | Trustpilot、SimilarWeb | 誰願意為這份資料付費？ |

## Phase 4：輕量驗證

> **動手寫程式碼之前，先用最便宜的方式確認假設是真的。**

| 驗證方式 | 成本 | 適合驗證什麼 |
|---------|------|------------|
| 問題訪談（5-10 人）| 免費 | 痛點是否真實存在、用戶理不理解你的解法 |
| Landing Page + 等候名單 | 0.5-1 天 | 有沒有人願意留 Email（意願強度）|
| Concierge MVP（人工後台）| 幾天 | 核心流程走不走得通，不需要任何程式碼 |
| 邀請制 Beta | 1-2 週 | 留存率與核心功能真實使用率 |

**進入開發的判斷標準**：
```
✅ 至少 5 位目標用戶確認「現有方案沒辦法解決我的問題」
✅ 核心流程用戶能理解，並願意走完
✅ 找到 1-2 個願意第一批試用並給真實回饋的「超級用戶」
```

## Phase 5：功能規劃（`/feature-plan`）

### MVP 邊界三問

對每個候選功能問：

1. **拿掉它，核心使用流程還走得通嗎？** → 走得通 → Phase 2
2. **這是「必須有」還是「有更好」？** → 有更好 → Phase 2
3. **用戶不用它，也能達成他的核心目標嗎？** → 能 → Phase 2

### 呼叫方式

```
/feature-plan [功能描述]
```

**輸出**：
1. 功能需求理解（用戶問題 / 目標用戶 / 成功指標 / MVP 邊界）
2. 技術任務清單（前端 / 後端 / DB，S/M/L 預估）
3. 影響範圍評估（業務邏輯？DB Schema？SEO？）
4. 自動更新 `plan.md`

## Phase 6：技術架構選型

根據你產品的核心需求做選型，不要選「最熱門的」：

| 需求 | 選型建議 |
|------|---------|
| SEO 是核心流量來源 | Next.js SSG/ISR；純 CSR 會傷害搜尋排名 |
| 高頻交易 / 金流操作 | Go / Rust；Node.js 在極高並發時要謹慎 |
| 1-2 人小團隊 | 選最熟悉的技術棧，學習成本是最大的隱性風險 |
| 快速驗證、低初期成本 | Vercel（前端）+ Fly.io（後端）+ Supabase（DB）|
| 需要即時同步 | WebSocket / SSE；REST 輪詢在這裡是反模式 |

**選型決策記錄模板**（決策的「Why」比「What」更重要）：

```markdown
## 技術選型決策記錄

| 層次 | 選擇 | 選擇原因 | 放棄的替代方案 |
|------|------|---------|--------------|
| Frontend | [技術] | [原因] | [替代方案及放棄原因] |
| Backend | [技術] | [原因] | [替代方案及放棄原因] |
| Database | [技術] | [原因] | [替代方案及放棄原因] |
| Hosting | [平台] | [原因] | [替代方案及放棄原因] |
```

## Phase 7：自動開發循環

> 這是整個流程最核心的部分。
> **讓 Claude Code 自主跑完「開發 → 測試 → 修正 → 文件」的完整循環，直到功能完成，中間不需要人介入。**

### 循環流程

```
┌─────────────────────────────────────────────────────────┐
│  你的指令：「請完成 plan.md 裡所有 Phase 1 的功能」       │
└──────────────────────────────┬──────────────────────────┘
                               ▼
              ┌────────────────────────────┐
              │  讀取 plan.md              │
              │  確認任務清單與優先順序      │
              └──────────────┬─────────────┘
                             ▼
              ┌────────────────────────────┐
              │  開發實作                  │
              │  - 前端元件               │
              │  - 後端 API              │
              │  - DB Migration          │
              └──────────────┬─────────────┘
                             ▼
              ┌────────────────────────────┐
              │  /qa-review               │
              │  BDD 測試（Given-When-Then）│
              │  每個 User Story 都要測     │
              └──────────────┬─────────────┘
                             ▼
               ┌─────────────┴─────────────┐
            全部通過？                   有失敗？
               ↓                           ↓
         git commit                    修正問題
         語意化訊息               回到「開發實作」重跑
               ↓
    ┌──────────────────────────────┐
    │  有新問題需要調查？           │
    │  → /research [問題]         │
    │  → 整合洞察，繼續下一個功能  │
    └──────────────────────────────┘
               ↓
         下一個功能（回到頂部循環）
```

### 觸發自動循環的指令範本

直接貼進 Claude Code 對話視窗：

```
請完成 plan.md 中標記「待開發」的所有 Phase 1 功能。

每個功能完成後：
1. 執行 /qa-review 測試
2. 修正所有發現的問題
3. git commit（語意化訊息）
4. 繼續下一個功能

如果遇到設計問題或不確定的技術決策，先用 /research 調查再繼續。
不要停下來詢問我，直到所有功能完成或遇到無法自行解決的阻礙。
```

### BDD 測試格式（`/qa-review` 使用）

從 User Story 出發，不是從功能清單出發：

```gherkin
Feature: [功能名稱]

  Scenario: [正常情況 — Happy Path]
    Given [前置條件]
    When  [用戶執行的動作]
    Then  [預期看到的結果]

  Scenario: [邊界情況 — Edge Case]
    Given [前置條件]
    When  [觸發條件]
    Then  [系統應該如何處理]

  Scenario: [異常情況 — Error Case]
    Given [前置條件]
    When  [觸發錯誤的動作]
    Then  [應該顯示什麼錯誤提示]
```

### 開發中何時觸發新一輪 `/research`

| 遇到的情況 | 觸發的研究問題 |
|-----------|--------------|
| 不確定某個功能怎麼設計 | `/research [功能類型] UX 設計最佳實踐` |
| 整合第三方服務 | `/research [服務名稱] API 限制與合規` |
| 遇到法律或隱私疑慮 | `/research [行為] [地區] 法規可行性` |
| 想優化某個留存機制 | `/research [你的產品類型] 留存策略` |
| 商業模式有調整 | `/research [新方向] 競品定價與可行性` |

## Phase 8：文件維護（`/sdd-update`）

### 觸發時機

每次 `git commit` 後：

```
/sdd-update
```

### 每個 PR 前確認的文件清單

- [ ] 系統設計文件（`sdd.md`）→ 有沒有新的 API 端點或 DB Schema 變動？
- [ ] 業務規則文件 → 核心邏輯有沒有改動？
- [ ] `CLAUDE.md` → 有沒有踩到新的坑，需要加進開發規則？

## 常見陷阱

### 開發陷阱

| 陷阱 | 症狀 | 解法 |
|------|------|------|
| Mock 資料留在生產頁面 | 用戶看到固定假資料 | 任何顯示用戶資料的頁面必須呼叫真實 API |
| API 格式假設錯誤 | 前端拿到 undefined 或解析失敗 | 先 `curl` 確認實際回傳結構，再寫前端呼叫 |
| 狀態變動後 UI 未同步 | 操作成功但畫面沒更新 | 操作完成後主動刷新相關狀態 |
| 副作用沒有觸發 | 核心操作完成，但關聯數據沒更新 | 每個 handler 完成後，列舉並觸發所有 side effects |
| Async callback 沒有 null guard | 元件 unmount 後 crash | callback 第一行加 `if (!ref.current) return` |
| 條件分支沒有涵蓋所有情況 | 特定類型觸發 404 或靜默失敗 | 明確列舉所有可能值，不依賴 else 兜底 |

### 產品陷阱

| 陷阱 | 症狀 | 解法 |
|------|------|------|
| 「驗證」設計成阻斷式門檻 | 用戶在完成核心操作前就被擋住 | 驗證應是「加分」不是「准入門檻」，不影響主流程 |
| SEO 頁面用純 CSR | Google 無法爬取，流量損失 | 任何需要被搜尋到的頁面，必須用 SSG/ISR |
| 核心操作可被刷 | 假帳號或自動化腳本刷數據 | 核心行為獎勵必須綁定真實可驗證的行為 |
| Scope Creep（範圍蔓延）| Phase 1 做了 Phase 3 的功能 | 每個功能先問「MVP 邊界三問」再開發 |

## Skills 速查

### Atomic Skills（單一任務）

| Skill | 觸發方式 | 使用時機 |
|-------|---------|---------|
| `/research` | `/research 主題` | 競品調查、市場研究、技術可行性、法規確認 |
| `/feature-plan` | `/feature-plan 功能描述` | 每個新功能開始前 |
| `/qa-review` | `/qa-review` | 每個功能實作完成後 |
| `/sdd-update` | `/sdd-update` | 每次 commit 後 |
| `/idea-to-mvp` | `/idea-to-mvp [Idea]` | 新專案從零開始，全流程引導 |

### 進階整合 Skills（從 atomic skills 上一層 orchestrator）

| Skill | 觸發方式 | 使用時機 | 內部呼叫 |
|-------|---------|---------|---------|
| `/auto-research` | `/auto-research [Idea 描述]` | 0→1 商機驗證一氣呵成（拆題→並行→synthesis→評分→驗證菜單）| `/research` × N、`/idea-to-mvp` Phase 2-3 + 5 + 6 |
| `/eli5-pptx` | `/eli5-pptx [專案代稱]` | 把 reports/ 的研究結論做成 16 slides 簡報 + 講者稿 | python-pptx + 4 預設配色 |

**何時用進階 vs atomic：**
- 0→1 階段、Idea 還很模糊 → `/auto-research`（自動跑完，省 1-2 小時）
- 已過商機驗證、進開發 → atomic skills（`/feature-plan`、`/qa-review`、`/sdd-update`）
- 隨時要驗一個小問題 → `/research`（單次）
- 要做投影片給人看 → `/eli5-pptx`（吃 reports/ 的內容自動生）

進階 skills 的所有產出**預設 ELI5 語氣**（用比喻不用術語、故事先於數字、不寫「待 X 確認」「AI 繼續觀察」），讓非技術讀者也能跟上。

## reports/ 命名規範

所有報告（研究、QA、Phase 產出）統一存到 `reports/`，命名規則：

```
reports/
├── {主題}-research-{YYYY-MM-DD}.md          ← /research 產出
├── qa-report-{YYYY-MM-DD}-{phase}.md        ← /qa-review 產出
├── {專案代稱}-phase{N}-{YYYY-MM-DD}.md       ← /idea-to-mvp 各 Phase 產出
└── screenshots/{date}-{phase}/              ← QA 截圖
```
